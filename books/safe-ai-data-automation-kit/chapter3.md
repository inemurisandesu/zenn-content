# 第3章：LLM/RAG投入前の決定的PIIマスキングと構造保持チャンキング

業務ドキュメントやCSV/JSONをLLMやRAGへ投入する際、「個人情報やAPIキーがそのまま外部モデルへ送られる」「見出しの文脈が切れて検索精度が落ちる」「同一内容が重複登録されてトークンを浪費する」という3つの課題が必ず発生します。

これらをLLM自身に頼まず、**決定的（同じ入力には常に同じ出力を返す・低コスト・高速）なPython処理**で前処理するのが実務の王道です。

## 1. NFKC正規化と空白整理

日本語・英語混在テキストは、まず `unicodedata.normalize("NFKC", text)` で全角英数字・記号の揺れを揃えます。これだけで後続の正規表現マッチ率と重複排除精度が大幅に安定します。

## 2. 決定的PII・シークレットのマスキング

外部APIへ渡す前に、最低限以下のパターンを正規表現でマスクし、**どの種別を何件マスクしたか（監査カウント）**をチャンク単位で記録します。

- メールアドレス → `[REDACTED_EMAIL]`
- APIトークン（`sk-...`、`ghp_...`、`AKIA...`、`AIza...` 等）→ `[REDACTED_TOKEN]`
- クレジットカード番号形式 → `[REDACTED_CARD]`
- 電話番号形式 → `[REDACTED_PHONE]`
- IPv4アドレス → `[REDACTED_IP]`

## 3. 見出し保持チャンキングとSHA-256重複排除

単純な固定文字数分割では、見出しと本文が分断されてRAG検索の文脈が壊れます。

1. Markdownの場合は `#`〜`######` の見出し単位でセクション分割し、各チャンクに `heading` メタデータを保持する。
2. セクションが目標サイズ（例：800文字）を超える場合のみ、段落（`\n\n`）→ 改行（`\n`）→ 空白の優先順で境界を探してオーバーラップ付き分割する。
3. 浄化済みチャンクのUTF-8バイト列から `hashlib.sha256` を計算し、既出ハッシュと一致した重複チャンクを自動スキップする。
4. ASCII文字（約4文字=1トークン）と日本語などの非ASCII文字（約1文字≒1.1トークン）を分けてトークン数を見積もる。

この前処理層を独立モジュールにしておけば、ローカルCLI・社内バッチ・クラウドAPIのどこからでも同じ品質で再利用できます。
