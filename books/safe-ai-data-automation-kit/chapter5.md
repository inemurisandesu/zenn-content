# 第5章：LLM出力の壊れたJSON修復とOpenAPIセキュリティ自動監査の実戦レシピ

最終章では、実務のAIワークフローとAPI開発の現場で即効性が高い2つの決定的ユーティリティ設計をまとめます。どちらも外部ネットワーク通信ゼロ・Python標準ライブラリ中心で構築でき、そのままApify StoreのPay-Per-Event Actorとしても稼働します。

## 1. LLM出力JSONの決定的修復レイヤ

LLMを業務フローに組み込むと、コードフェンス混入・末尾カンマ・シングルクォート・トークン上限による末尾欠損が一定の割合で発生します。

- **安全原則**：`eval()` は絶対に禁止し、`json.loads` → 構文クリーンアップ → スタックベースの括弧補完 → `ast.literal_eval` の順に段階的フォールバックする。
- **厳密な型検証**：Pythonでは `isinstance(True, int)` が `True` になるため、JSONスキーマの型検査は `type(v) is int` / `type(v) is bool` で厳密に判定する。
- **修復証跡の記録**：発動した修復ステップを `repairSteps` 配列として残し、上流プロンプトの改善シグナルとして活用する。

## 2. OpenAPI 3.xの自動セキュリティ監査＆破壊的変更検知

API仕様の変更時に「非TLSサーバーURL」「クエリ文字列内の機密パラメータ（`api_key` 等）」「壊れた内部 `$ref`」「既存エンドポイント削除や新規必須パラメータ追加」を自動検知する仕組みをCIやMCPツールに組み込んでおくと、レビュー工数と事故を同時に削減できます。

- **ゼロ外部通信設計**：`#/` から始まる内部JSON Pointerのみをローカル解決し、外部URL参照によるSSRFリスクを構造的に排除する。
- **定量スコア化**：`critical / high / medium / low` の減点テーブルで0〜100点を算出し、品質基準を機械可読にする。

## 3. 自己分析・自己修正ループへ繋げる運用設計

単発でツールを作って終わりにせず、以下の4段階を継続的に回すことでプロダクト資産が複利で積み上がります。

1. **計測**：GitHubトラフィック・実行ログ・エラー率・利用回数を機械可読なJSONに定期記録する。
2. **分析**：失敗ケース・想定外フォーマット・問い合わせの多いユースケースを抽出する。
3. **修正＆検証**：必ず先に失敗を再現するユニットテストを追加してから修正し、全テスト通過を確認する。
4. **自動配信**：`git push` でコード・Apifyビルド・Zennドキュメントを同時に最新化する。

本書で紹介したすべての設計パターンは、実際の公開リポジトリ（`portfolio-automation-kit` / `apify-rag-data-normalizer` / `apify-openapi-spec-auditor` / `apify-llm-json-repair-validator`）でテスト済みの実装として参照できます。
